# MPI PatchCore 정상 개발자료 확대 결과 검토

2026년 10월 8일. 같은 정상 256장 학습 모델을 유지하고, 정상 척도 개발자료만 128장에서 256장으로 늘렸다. **불량 55장 검출을 유지하고 개발자료 재표집에 대한 안정성은 개선했지만, 오경보와 전체 보정 안정성 목표는 미달했다.** 이번 보정 계약을 운영에 채택하지 않고 연구 후보로 보존한다. 기존 모델·계약·서비스는 변경하지 않았다.

## 고정 자료에서의 결과

| 항목 | 개발 128장 | 개발 256장 |
| --- | ---: | ---: |
| 불량 검출 | 55/55 | 55/55 |
| 미탐 | 0 | 0 |
| 정상 시험 오경보 | 1/54 (1.85%) | 1/54 (1.85%) |
| 별도 정상검증 오경보 | 16/256 (6.25%) | 15/256 (5.86%) |
| 공식 시험 109장 이미지 AUROC | 1.000 | 1.000 |
| 기존 검출 12장 유지 | 12/12 | 12/12 |
| 사진 경고선 | 3.0014441770 | 3.1629022908 |

검출 55/55 유지와 오경보 ≤2/54는 통과했다. 오경보 ≤12/256은 실패했다. AUROC 1.000은 불량 55장과 정상 시험 54장만의 비교이며 별도 정상검증 256장까지 완벽히 분리한다는 뜻이 아니다. 이미 관찰한 자료에 대한 탐색·회귀검증이며 새로운 일반화 성능의 증거가 아니다.

해결된 오경보는 `validation/0853` 한 장이고 새 오경보는 없다. 해당 사진의 grid1-1 원점수는 그대로지만 영역 경계가 41.7493에서 43.2387로 올라갔다. 사진 점수는 3.4640에서 3.0474로 변해 새 경고선보다 낮아졌다. 이전 시각 검토에서 왼쪽 검은 여백·기판 경계에 반응했던 사례다. 이번에는 이미지를 다시 검사하거나 지도 반응을 바꾼 것이 아니다.

## 정상 자료 구성에 대한 민감도

개발자료는 정상 점수의 중심·폭을 계산하는 사진이며, 보정자료는 그 점수를 이용해 사진 경고선을 정하는 정상 169장이다. 각 조건 200회씩, 총 600회 복원추출했다.

| 다시 뽑은 정상 자료 | 50장 미만 검출 시행 기존→후보 | 검출 하위 2.5백분위 기존→후보 | 후보 목표 |
| --- | --- | --- | --- |
| 개발자료만 | 12/200 → 4/200 | 35.95 → 51.00 | 통과 |
| 보정자료만 | 1/200 → 1/200 | 50.00 → 51.00 | 오경보 목표 실패 |
| 개발·보정 모두 | 27/200 → 11/200 | 24.975 → 43.975 | 검출·오경보 목표 실패 |

양쪽을 다시 뽑았을 때 평균 미탐은 3.02장에서 1.02장으로 줄었다. 검출 백분위 폭도 30.025장에서 11.025장으로 감소했다. 그러나 정상검증 오경보 상위 97.5백분위는 28.025장에서 32장으로 증가했고, 정상 시험 오경보 상위값은 7장으로 동일했다. 목표는 각각 25장·5장 이하다. 모든 종류의 안정성이 함께 개선된 것은 아니다.

개발자료만 바꾼 후보도 최악 시행은 39/55 검출이었다. 해당 목표 통과는 사전 지정한 백분위 기준을 통과했다는 뜻이지 모든 시행이 안전하다는 뜻이 아니다. 세 조건 모두 무효 시행은 0이다. 이 백분위는 현재 자료의 재표집 민감도이며 모집단 성능 신뢰구간이 아니다. 두 비교는 보정 인덱스를 공유하지만 개발 집합 크기와 재표집 난수는 다르므로 개발 인덱스까지 동일한 짝 비교가 아니다.

## 경고선 숫자만으로는 해결할 수 없는 부분

새 점수에서 가장 낮은 불량은 `defect/0024`로 3.4586024516이다. 별도 정상검증 256장 중 **14장의 점수가 이 값 이상**이다. 경고 규칙이 점수 ≥경고선이므로, 현재 점수를 고정하고 불량 55장을 모두 검출하려면 경고선은 이 값 이하여야 하며 정상 오경보는 최소 14장 남는다. 따라서 경고선만 바꾸어 55/55 검출과 ≤12/256 오경보를 동시에 달성할 수 없다.

이는 관찰 자료의 점수 순서를 설명하는 진단이지 불량 라벨로 새 경고선을 선택한 것이 아니다. 실제 경고선은 변경하지 않았다. 개발 128장 기준의 같은 이론적 최소 오경보는 13장이었다. 현재 경고선에서 오경보가 한 장 감소한 것과 정상·불량의 점수 순서가 전반적으로 더 좋아진 것은 구별해야 한다.

보정만 재표집한 후보 경고선의 2.5·50·97.5백분위는 2.3638·3.1629·3.8108이다. 높은 경고선은 낮은 점수의 불량을 놓치고 낮은 경고선은 정상 경고를 늘릴 수 있다. 고정 경고선의 순위 사진은 `calibration/1671`의 grid2-1이며, 169장 중 아홉 번째로 높은 사진 점수다. 이 사진이 잘못된 정상이라는 뜻은 아니다.

## 실행과 무결성 검증

- 전달 ZIP: `mpi-patchcore-development-scaling-v1.zip`.
- SHA256: `992b0c47ef2b2ee4641077ad2ca75b2d07533bfedf776c903473cdb352e609b8`.
- ZIP CRC·중복 이름·파일 목록·12개 payload 해시가 통과했다.
- 실행 소스 209개의 LF 정규화 해시와 고정 정책·부모 실행·환경·기존 계약·기존 점수 지문이 일치했다.
- 추가 128장의 명단·1,536개 영역 지문, 현재 학습·개발·보정·검증 자료의 ID 분리 및 시험을 포함한 보호 자료의 RGB 지문 분리를 재검증했다.
- 보고된 적격 풀 1,086장 중 후보 774장에서 128장을 선택했다. 선정된 명단의 해시 순서는 확인했다. 원래 풀 ZIP과 과거 학습 64장 전체 목록은 이번 수령물에 없으므로 전체 풀의 적격 수와 최상위 128장 선택, 과거 64장 분리는 로컬에서 독립 재실행하지 못했다. 해당 부분은 해시 고정 실행 코드와 실행 기록에 근거한다.
- 예측 영수증 128개의 자체 해시·실행 ID·모델 ID·사진 ID·샘플 JSON 지문이 일치했다.
- 추가 정상 점수와 이전 결과 ZIP을 이용해 새 계약·모든 사진 판정·AUROC·변경 사례·영역 경계·600회 재표집 및 통과 기준을 전부 다시 계산했다. 구조와 건수는 동일하고 실수 최대 차이도 0이었다.
- 기존 정상 8장 점수·지도 재현과 새 정상 8장 모델 재로딩 검사는 모두 최대 차이 0, 판정 변경 0으로 기록됐다.
- 원본 이미지·지도 배열·모델 실물은 포함되지 않았다. 영수증 일치를 모델 파일 재해싱·지도 원점수 재산출·GPU 재추론으로 표현하지 않는다.

한 번의 실행에서 176.781초, 약 2분 57초가 기록됐다. 프로세스 RAM 표본 최고 2.604GiB, PyTorch GPU allocated 최고 2.668GiB, reserved 최고 2.928GiB, 장치 전체 사용 표본 최고 4.064GiB였다. 장치 전체 사용량은 해당 모델만의 메모리가 아니다. 176.781초는 기록된 실행 시도 구간으로 시작 전 입력 검증과 최종 재검증·ZIP 저장까지 모두 포함한 벽시계 시간은 아니다. 새 검사 속도 벤치마크는 수행하지 않았다.

## 다음 단계 제안

이번 개발자료 확대는 효과가 없는 실험이 아니다. 정상 범위 추정의 흔들림이 줄어든 연구 근거로 보존하되 운영 승인은 보류한다. 다음에는 재학습이나 보정자료 자동 확대보다 **현재 점수로 가장 약한 불량보다 높게 평가되는 정상 14장과 그 불량 0024의 점수·영역 반응을 대조**하는 것이 우선이다.

1. 기존 저장 점수로 원점수, 정상 중심·폭, 경고선을 분리한다. 이번 정상 14장 중 주 반응 영역은 13장이 0024의 grid3-2와 다르고 한 장은 동일하다. 영역 간 척도 영향과 같은 영역 내 구분 문제를 구별한다.
2. 필요한 사례의 기존 저장 지도와 원본을 비교해 실제 반응 위치를 확인한다. 그림을 보기 전 여백·반사·부품 누락 같은 원인을 단정하지 않는다.
3. 보정자료 재표집의 경고선 불안정은 별도로 관리한다. 보정자료 추가는 이 부분을 줄일 후보일 수 있지만, 고정 점수에서의 최소 오경보 14장 한계는 해결하지 못한다.

그 근거를 바탕으로 다음 변경 한 가지를 정한다. 원점수·영역 척도를 고정한 채 경고선만 조정하는 실행은 현재 목표를 해결할 다음 실험으로 제안하지 않는다. 이미지 삭제, 오경보의 개발자료 이동, 경고선 수동 조절, 모델 교체, 자동 PASS는 없다. 이번 검토에서는 새 실행기를 만들거나 연구실 작업을 시작하지 않았다.
