# DefectOps · 이력서에 사용할 핵심 성과 3가지

정리 기준: 2026-11-14. 저장소 코드와 실행 보고서에 근거한 프로젝트 성과다. 개인 이력서에 사용할 때는 실제로 본인이 담당한 설계·구현·실행·검증 범위에 맞춰 주어와 동사를 조정한다. 아래는 현장 배포나 독자 알고리즘 개발을 주장하지 않는 문안이다.

## 프로젝트 소개

**DefectOps | 정상 데이터 기반 제조 이미지 이상탐지·작업자 검토 프로토타입**

Python, PyTorch/Anomalib, FastAPI, Streamlit, SQLite를 사용해 모델 비교·검사 API·사람 검토·근거 문서·승인 이력을 구현했다. 공개 데이터 실험에서 정확도뿐 아니라 오경보·메모리·추론 시간·보정 안정성을 함께 검증했다.

## 1. 모델 비교와 실패 분석을 통한 선택 근거 구축

**이력서 문안**

> 정상 데이터 기반 PaDiM·PatchCore 구성을 동일 Transistor 시험 자료에서 3개 seed로 비교해 평균 불량 검출률 60.0%와 92.5%를 확인하고, 미탐·오경보 분석을 근거로 PatchCore를 검사 프로토타입 후보로 선정.

**면접에서 설명할 내용**

- 문제: 순위 지표가 높아도 고정 임곗값에서 불량을 놓칠 수 있다.
- 접근: 검출·오경보·위치 지표·속도를 함께 비교하고 원본과 이상 지도로 실패 사례를 확인했다.
- 결과: PatchCore는 세 seed 모두 불량 37/40장 검출, 정상 1/60장 경고로 판정이 동일했다. 평균 검출률 차이는 32.5%p다.
- 판단: 미탐 3장이 남아 자동 합격을 허용하지 않고 사람 검토를 유지했다.

**수치의 범위:** 정상 학습 170장, 보정 43장, 시험 정상 60장·불량 40장. 동일 시험 자료를 반복 관찰한 탐색 비교다. 특징 추출기도 다르므로 알고리즘만의 개선 효과나 독립적인 현장 성능으로 표현하지 않는다.

## 2. 8GB GPU 제약에서 대규모 특징 처리와 실행 복구 구현

**이력서 문안**

> GPU 메모리 제약에 대응해 PatchCore 특징의 디스크·CPU 보관, 분할 처리와 중간 저장·재개를 구현하고, 약 314만 개 후보에서 78,643개 대표를 구성하는 실험을 GPU reserved 최대 2.93GiB로 완료.

**면접에서 설명할 내용**

- 문제: 전체 특징과 거리 계산 중간 배열을 GPU에 올리는 실행에서 메모리 부족이 발생했다.
- 접근: 특징 저장과 대표 선정 단계를 분리하고, 후보를 나누어 전송·계산하며 진행 상태를 보존했다.
- 결과: 원특징 대표 선정·보정·재로딩을 약 14시간 30분에 완료했다. 프로세스 RAM RSS 표본 최대는 13.413GiB였다.
- 판단: 메모리 절감에는 긴 실행 시간이라는 비용이 있다. 학습 준비 시간과 사진 1장·12영역 warm 추론 평균 약 1.16초를 구분해 기록했다.

**수치의 범위:** MPI-PCB 정상 학습 사진 256장, 특징 후보 3,145,728개. 2.93GiB는 PyTorch reserved 값이며 장치 전체 사용량이 아니다. 기존 실패 실행과 입력 규모·조건이 같지 않으므로 단순한 메모리 절감률이나 속도 향상률을 만들지 않는다.

## 3. 모델 결과와 사람 판단을 연결하는 검토·승인 이력 구현

**이력서 문안**

> FastAPI 상주 추론 API와 Streamlit·SQLite 검토 흐름을 구현하고, 검토 개정·SOP 원문·승인·모의 티켓을 연결해 수정 충돌, 오래된 승인 재사용 및 모의 티켓 중복 발행을 방지.

**면접에서 설명할 내용**

- 문제: 의견이 바뀐 뒤 예전 승인이 사용되거나, 같은 조치가 중복 기록되면 결과를 추적하기 어렵다.
- 접근: 모델 결과와 사람 의견을 분리하고, 의견 수정은 새 개정으로 저장했다. 근거·승인·티켓에는 같은 검토 개정만 연결하도록 제한했다.
- 결과: 실제 검사 결과 한 건으로 사람 검토 → 모의 SOP → 승인 → 로컬 모의 티켓 시연을 완료했다.
- 확장: 별도 MPI 입력 관찰 화면에는 사진·영역, 검사 범위의 근거, 판단 불가 이유, 작성자·시각·수정 이력을 저장하도록 구현했다.

**구현의 범위:** 검사 결과는 파일로 전달한 뒤 CLI로 검토 저장소에 등록한다. 자동 통합·인증된 사용자 권한·외부 티켓 연동·현장 운영은 미구현이다. 중복 방지는 검토/티켓의 해당 저장 경로에 대한 기능이며 모든 HTTP 검사 요청의 중복 방지를 뜻하지 않는다. MPI 의견 기능은 기존 서비스와 분리되어 있다.

## 자기소개서에서 사용할 문제 해결 흐름

세 성과를 모두 길게 나열하기보다 지원 직무에 맞는 한 사례를 선택한다.

| 지원 분야 | 중심 사례 | 설명할 판단 |
| --- | --- | --- |
| ML·컴퓨터 비전 엔지니어 | 성과 1 + 성과 2 | 모델 선택의 기준, 오류 분석, 장비 제약과 비용 |
| AI 서비스·백엔드 | 성과 3 + 성과 2 | 기록 일관성, 실패·재시도, 모델 실행과 서비스 경계 |
| 연구 지향 직무 | 성과 1의 분석 과정 | 통제한 조건, 실패 가설, 독립 평가와 탐색의 구분 |

추천 서술 순서: **발생한 문제 → 본인이 확인한 원인 → 선택한 변경 → 측정 결과 → 남은 한계와 결정**.
AI 지원을 받은 구현과 본인이 직접 설계·실행·검토한 작업을 구분해 설명할 준비를 한다. 실험 횟수·코드 양·테스트 개수 자체를 핵심 성과로 삼지 않는다.

## 시각 자료 선택

- **README에 반영:** 검사→파일 전달·등록→검토→승인 흐름도. 실제 수동 연결 단계를 표시한다.
- **README에 반영:** 동일 자료의 3-seed 평균 검출률 막대그래프. 0–100% 축과 탐색 비교 조건을 함께 표시한다.
- **후속 시연에 적합:** 합성 이미지·별도 데모 DB로 검토 수정과 오래된 승인 거부를 보여주는 짧은 화면 녹화. 현재 실제 화면 캡처나 영상이 공개되어 있다고 주장하지 않는다.
- **제외:** 다른 데이터셋의 성능을 한 순위로 합친 그래프, 실제 UI처럼 만든 가상 화면, 원본 연구 이미지나 실제 작성자 의견의 무단 공개.
