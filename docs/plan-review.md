# 초기 계획 검토 — 2026-09-12

## 결론과 확정 범위

비전 이상탐지를 핵심으로 두고 LLM을 근거 검색·문서 작성에 한정하는 방향은 적절하다.
다만 첨부안 전체는 한 번에 만들기에는 크다. 1차 목표는 **transistor + PaDiM + 재현 가능한 평가**,
최종 MVP는 PaDiM/PatchCore × 3품목 + 작업자 검토 + 모의 SOP/티켓으로 둔다.
EfficientAD·AD 2·고급 드리프트·모델 변환은 별도 확장이다. 8주는 확약 일정이 아니라 단계별 추정이다.

## 보완해야 할 판단

### 1. 99.5% 분위수는 정상 표본 수에 비해 지나치게 높다

예를 들어 정상 calibration이 40장이면 상위 0.5%는 표본 0.2장에 해당한다.
분위수는 계산 가능하지만 정상 오탐률 0.5%를 검증했다는 뜻은 아니다.
파일럿은 95% 경험적 분위수(`higher`)를 사전에 고정하고 표본 수와 불확실성을 함께 보고한다.
이는 보수성/안전성 보장이 아니라 초기 가상 운영점이다. 검증 세트에서 관찰한 오탐률도 일반화 보장이 아니다.
미탐률은 정상 표본만으로 보정할 수 없다. 99.5%를 쓰려면 충분한 별도 정상 검증 표본을 확보하는 계획이 필요하다.

### 2. 테스트를 보고 우승 모델을 튜닝하는 절차는 수정한다

고정된 여러 후보를 공식 test에서 비교하는 것은 가능하다. 그 결과로 선택된 모델의 성능은
선택 편향을 포함하므로 독립적인 배포 성능 추정이라고 표현하지 않는다.
테스트 결과를 보고 입력 크기/coreset/후처리를 바꾼 결과는 탐색 결과로 분리한다.
추가 튜닝이 필요하면 미리 분리한 labeled development/custom holdout Protocol B 또는 새 평가셋을 사용한다.
Protocol A에서는 모든 후보·seed·평가 지표·후처리 규칙을 test 열기 전에 고정한다.

### 3. Anomalib 기본 동작을 그대로 쓰면 프로젝트 프로토콜과 달라질 수 있다

공식 문서는 validation에서 F1을 최대화하는 adaptive threshold를 설명하며,
정상 validation만 있는 경우 최대 관측 점수를 사용한다고 명시한다.
따라서 단순히 기본 datamodule와 Engine을 연결하는 예제로는 충분하지 않다.
설치할 버전에서 split 생성과 validation 경로를 확인하고, manifest 전용 loader와 원시 점수 기반의
별도 calibration을 사용해야 한다. 최종 판정 임곗값/정규화는 모델과 함께 버전 관리한다.
모델 내부 map 정규화가 필요한 경우에도 calibration 출처를 기록하고 test 통계를 쓰지 않는다.
[근거: Anomalib post-processing](https://anomalib.readthedocs.io/en/latest/markdown/guides/how_to/models/post_processor.html)

### 4. 모델 학습용 seed와 분할 seed는 별도다

분할 seed는 모든 실험에서 42로 고정한다. 모델 seed 42/43/44 변경 시 분할은 바꾸지 않는다.
PaDiM도 특징 차원 선택을 사용하므로 단일 seed에서 재현된다는 사실이 seed 변동이 없다는 뜻은 아니다.
PaDiM도 최종 비교에서는 3회로 맞춘다. 첫 연결 확인용 실행만 seed 42로 한다.
[근거: PaDiM 논문](https://arxiv.org/abs/2011.08785)

### 5. 이미지 판정 임곗값과 영역 추출 임곗값을 분리한다

원시 점수·원시 anomaly map을 저장하고, AUROC/AP/AUPRO는 표시용 0–1 clipping 이전 값으로 평가한다.
이미지마다 min-max한 히트맵은 정상 이미지도 붉게 보일 수 있으므로 판정 근거로 사용하지 않는다.
표시 범위는 calibration으로 고정하고 범례를 제공한다. 픽셀 임곗값은 별도로 정하며
normal-only 방식은 결함 경계 정확도를 최적화했다는 의미가 아니다.
MVP morphology는 끄고 시작한다. 작은 결함을 지우는 위험을 먼저 확인한다.
원본 좌표 변환·bbox 끝점 규칙·resize 방법을 명시한다.

### 6. 대시보드에서 운영 미탐률을 바로 계산할 수 없다

검토 요청된 건만 라벨을 달면 PASS 중 불량(FN)을 모른다.
초기 대시보드는 검토율·검사 실패율·검토 건 중 정상 비율·피드백 완료율을 보여준다.
검토 건 중 정상 비율은 FP/(TP+FP)이며, 원래 정의한 overkill FP/(TN+FP)와 다르다.
실제 미탐률/오탐률은 공식 라벨이 있는 오프라인 평가와 분리하고,
운영에서는 PASS 무작위 표본 검사·표본 추출 확률·라벨 지연을 기록한 후 추정한다.
MVTec의 불량 비율은 실제 현장 유병률과 다르므로 test의 Precision/Review Rate를 현장 수치로 옮기지 않는다.

### 7. 정형 SOP 검색에서는 RAG 필요성부터 비교한다

제품·작업자 결함 유형·유효 개정판을 정확히 필터링하는 검색을 첫 기준선으로 둔다.
문서 15개에 반드시 벡터 DB가 필요한 것은 아니다. 자유 입력 검색에서 개선이 있을 때 embedding을 추가한다.
60개 질의는 단순 표현 변형만으로 채우지 않고 unknown·문서 없음·다른 품목·폐기된 개정판·인용 오류를 포함한다.
검색 튜닝용과 최종 평가 질의는 나누고, 필요하면 변형 문구 대신 SOP/의도 그룹 기준으로 분할한다.
인용 ID가 존재하는 것과 주장 내용이 근거에 의해 뒷받침되는 것은 별도 평가다.
LLM 없이도 검증된 원문 절과 템플릿 초안을 표시하도록 fallback을 둔다.

### 8. 승인과 중복 방지는 서버 상태 전이로 보장한다

검사 판정, 사람 판정, 초안, 승인, 실제 모의 티켓 생성을 별도 상태로 관리한다.
초안 수정 시 revision을 증가시키고 승인 요청은 해당 revision·검토 버전·SOP 개정판을 검증한다.
티켓 생성과 승인 상태 변경은 하나의 SQLite transaction으로 처리하며 유일 키 충돌도 처리한다.
첫 MVP는 검사 ID + tool 이름당 티켓 한 개로 제한한다. 이후 재발행은 명시적 새 시도 ID가 필요하다.
mark_false_positive는 LLM 실행 tool이 아니라 작업자 피드백 API로 옮긴다.
정비 티켓은 이미지로 원인을 추측해 발행하지 않고 승인된 모의 SOP 조건이 있을 때만 제안한다.

### 9. 배포 목표 하드웨어를 먼저 고정한다

맥 ARM CPU와 연구실 x86 CPU/GPU 수치는 별도로 보고한다. Docker 안의 CPU와 맥 native/MPS도 구분한다.
모델 변환은 형식 생성 성공 외에 원시 점수·맵 오차·임곗값 인접 사례의 판정 일치와 전체 p95를 검증한다.
PyTorch/Anomalib 버전·가중치 checksum·전처리 설정을 고정하되 CUDA wheel/환경은 장비별로 관리한다.
SQLite DB는 맥북 데모 인스턴스가 관리하고 연구실은 실행 산출물만 돌려준다.

### 10. 입력 품질 검사는 가능한 항목부터 구현한다

파일 크기·디코딩·해상도는 검증할 수 있다. 밝기/블러는 train/calibration 기준을 정한 후 휴리스틱으로 도입한다.
제품 종류/위치 이탈을 자동으로 정확히 판별하려면 별도 검증이 필요하다.
첫 MVP는 제품 선택을 작업자 입력으로 신뢰하되 UI에 이를 표시하고, 오류 시 자동 PASS를 금지한다.

## 데이터 이용 범위

MVTec AD는 정상 학습 이미지, 정상/이상 테스트 이미지, 이상 위치 주석을 제공한다.
AD 2는 별도 시나리오 데이터이므로 AD 모델을 그대로 넣는 동일 품목 조명 실험으로 설명하지 않는다.
AD 2 확장 시 해당 품목의 정상 학습 데이터로 별도 모델을 구축하며 private test는 공식 서버 평가가 필요하다.
두 데이터셋의 비상업·출처·동일조건변경허락 조건을 데이터 및 파생물에 별도로 기록한다.
포트폴리오라는 명칭만으로 모든 이용이 자동 허용된다고 해석하지 않는다.
